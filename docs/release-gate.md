# Релизный gate для 1С

## Цель

Gate должен отвечать отдельно на два вопроса:

1. Появились ли новые регрессии относительно известного состояния?
2. Разрешено ли выпускать артефакт с оставшимися известными проблемами?

Известное падение теста не считается новой регрессией, если совпадают платформа,
архитектура, ID сценария и сигнатура ожидаемой ошибки. Оно остаётся видимым в
отчёте и не превращается в успешный тест.

## Этапы прогона

1. **Preflight:** зафиксировать версии платформы 1С, EDT и архитектуру; проверить
   наличие входных пакетов и доступность лицензии для тех шагов, которым она нужна.
   Проблемы окружения получают статус `blocked`.
2. **Быстрые проверки:** Python unit-тесты, целостность метаданных и соответствие
   исходников свежему EDT-экспорту.
3. **EDT:** экспорт проекта и проверка конфигурации. Ошибки конфигурации блокируют
   прогон. Значимые замечания допускаются только при точном совпадении правила,
   объекта и текста с `edt_known_significant` в baseline. Незначительные и
   тривиальные замечания записываются в отчёт и не блокируют релиз. Полный
   EDT-отчёт сохраняется в артефактах.
4. **Пакеты:** собрать `.cf` и `.cfe`, загрузить и проверить их в чистых базах,
   применить, затем выполнить обратный экспорт для сравнения исходников.
5. **Платформа 1С:** выполнить `CheckConfig` в заявленных клиентских и серверных
   режимах; запустить runtime-набор на CF и CFE.
6. **Сверка и упаковка:** проверить полноту отчётов, сравнить падения с baseline,
   записать статусы и хеши в `manifest.json`, проверить архив и его контрольные
   суммы.
7. **Публикация:** отдельный шаг загружает только разрешённый манифестом архив.
   В этот репозиторий пока не добавлен автоматический uploader релиза.

Лицензия и платформа не попадают в Git или Docker image. EDT-export и сборочные
команды можно запускать в одноразовом контейнере. Runtime-проверки выполняются в
контейнере, где лицензия действительно доступна, либо через настроенный сервер
лицензий. Пропущенный из-за лицензии шаг не считается PASS.

## Сверка runtime-baseline

`tests/release-baseline.json` содержит известные ошибки, отдельно для версии
платформы и архитектуры. Сейчас в нём есть baseline для Linux ARM64, 1С
8.5.1.1529. Для других платформ baseline отсутствует, поэтому любое падение там
считается новым.

Каждое исключение содержит ID runtime-сценария, номер issue и фрагмент старой
ошибки. Проверка допускает его как `baseline-only` только при совпадении всех
трёх условий. Любое новое падение, другая ошибка того же теста, пропущенный,
дублированный или неизвестный тест блокирует выпуск. Ранее падавший тест, который
теперь прошёл, показывается как `resolved_baseline_failures`.

Правила сопровождения baseline:

- добавлять только подтверждённые прежние ошибки после сравнения базовой и
  изменённой версий в одинаковом окружении;
- привязывать запись к конкретной платформе, архитектуре, тесту и issue;
- не перегенерировать список автоматически из отчёта кандидата;
- удалять запись, когда тест исправлен, и не переносить исключения на другие
  версии платформы или архитектуры без отдельного прогона.

В текущем baseline перечислены 14 прежних падений по #6, #7 и #9. Они повторились
в прогоне 1.0.5.1 без появления новых ошибок. Шесть сценариев #19 не входят в
baseline, поэтому любое их падение блокирует прогон.

Для EDT в том же файле перечислены две уже известные значимые диагностики по
описанию возвращаемых свойств. Новая значимая диагностика блокирует прогон;
незначительные и тривиальные видны в `severity_counts` манифеста и полном TSV.

## Итоговые статусы

| Статус манифеста | Значение | Публикация по умолчанию |
| --- | --- | --- |
| `verified` | Все обязательные проверки прошли, новых runtime-падений нет | Разрешена |
| `baseline_only` | Новых падений нет, остались только совпавшие baseline-ошибки | Запрещена |
| `verified_with_baseline` | Только baseline-ошибки; явно разрешён выпуск с известными проблемами | Разрешена с таким статусом в манифесте |
| `candidate` | Появилась новая ошибка либо отчёт неполон/некорректен | Запрещена |
| `blocked` | Не хватает лицензии или обязательного окружения | Запрещена |
| `source_dirty` / `source_unknown` | Рабочее дерево изменено или исходную ревизию нельзя установить | Запрещена |
| `build-failed` | Сборка, установка или обратная проверка CF/CFE не прошла | Запрещена |

`ALLOW_KNOWN_BASELINE_FAILURES` по умолчанию выключен. Установка в `true` —
явное разрешение выпускать пакет со статусом `verified_with_baseline`; она не
разрешает новые ошибки и не меняет результат отдельных тестов. Без этой опции
baseline-only прогон создаёт только локальный архив `-rc1` и возвращает код 2.
Даже с этой опцией исходники должны быть на чистой Git-ревизии. Локальные
изменения дают `source_dirty`; отсутствие Git SHA даёт `source_unknown`.

Коды завершения `scripts/run-container-release.sh`:

- `0` — `verified` либо явно разрешённый `verified_with_baseline`;
- `1` — новый runtime-сбой или ошибка проверки;
- `2` — только baseline-сбои, выпуск не разрешён;
- `3` — запуск заблокирован окружением или лицензией;
- `4` — исходники изменены или ревизия не определена;
- `5` — не собрался CF/CFE или не прошёл round-trip.

## Связь с issues

У каждой задачи должны быть перечислены тесты, проверяющие её критерии приёмки.
Issue закрывается после прохождения именно этих тестов в режимах, на которые
распространяется изменение. Допуск baseline для релиза не означает, что связанная
с ним issue выполнена. Публикация релиза проходит отдельный общий gate.

## Как запускать

Строгий прогон, без разрешения baseline-ошибок:

```sh
ONEC_PACKAGE_DIR=/path/to/linux-platform-debs \
EDT_HOME=/path/to/edt-installation \
EDT_PLUGIN_POOL=/path/to/edt/plugins \
ONEC_LICENSE_DIR=/path/to/valid-linux-licenses \
./scripts/run-container-release.sh
```

Разрешить выпуск с совпавшими baseline-ошибками можно только отдельным решением:

```sh
ALLOW_KNOWN_BASELINE_FAILURES=true \
ONEC_PACKAGE_DIR=/path/to/linux-platform-debs \
EDT_HOME=/path/to/edt-installation \
EDT_PLUGIN_POOL=/path/to/edt/plugins \
ONEC_LICENSE_DIR=/path/to/valid-linux-licenses \
./scripts/run-container-release.sh
```

В обоих случаях сборка сохраняет отчёты и `manifest.json` в новом каталоге
`build/release-run.*`. Манифест содержит Git SHA и состояние рабочего дерева.
Перед загрузкой архива uploader должен проверить `release_allowed: true`, чистую
ревизию, совпадение версии тега с версией конфигурации и SHA256 тех же файлов,
которые публикуются.
