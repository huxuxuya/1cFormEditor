# Модуль изменения управляемых форм

При доработке типовых конфигураций, для уменьшения издержек на сопровождение конфигурации при ее обновлении, доработка форм должна производиться с максимальным приоритетом программной доработки.

Целью модуля является упрощенное добавление реквизитов формы, добавление их на форму (в том числе и таблиц), так же добавление групп, команд формы и кнопок к ним.

[Быстренько посмотреть актуральный код модуля]( https://github.com/huxuxuya/1cFormEditor/blob/master/FormEditor/src/CommonModules/%D0%A0%D0%B5%D0%B4%D0%B0%D0%BA%D1%82%D0%BE%D1%80%D0%A4%D0%BE%D1%80%D0%BC/Module.bsl)

### Установка

Установка производится через сравнение/объединения конфигурации с файлом поставки, с установкой на поддержку.

#### Предварительные требования

Модуль распространяется поставкой. 
Зависимостей не имеет.

### Обновление

Обновление производится через обновление с сохранением конфигурации поставщика
Для проверки корректности совместимистои версий необходимо открыть обработку тестирования обновляемой версии(которая входит в поставку) на версии, на которую будет обновлен модуль.

## Начало работы

### Предварительная подготовка

Необходимо добавить вызов процедуры, содержащей код программного добавления в самое начало следующих процедур:
 * ПриСозданииНаСервере()
 * ПриЧтенииНаСервер() - если форма имеет возможность открытия существующего объекта
  
 <details>
  <summary>Пример кода подготовки</summary>
	
 ``` bsl
&НаСервере
Процедура ПриЧтенииНаСервере(ТекущийОбъект)
	ПрефиксПодготовитьФорму();
	//Текст процедуры	
КонецПроцедуры 	

 &НаСервере
Процедура ПриСозданииНаСервере(Отказ, СтандартнаяОбработка)
	ПрефиксПодготовитьФорму();
	//Текст процедуры	
КонецПроцедуры 

&НаСервере	
Процедура ПрефиксПодготовитьФорму()
	Если РедакторФорм.ФормаПодготовлена(ЭтаФорма) Тогда
		Возврат;
	КонецЕсли;
	//Код изменения формы
КонецПроцедуры 
```
</details>

**Данная архитектура необходима:**
* Для возможности отображения данных, которые находятся не в самом объекте. 
* Для корректной настройке формы, которая должна происходить при чтении объекта, до вызовая создания на сервере.

Так же данный подход позволяет использовать типовые процедуры, например **УправлениеФормой()**.

## Запуск тестов

Тесты запускаются через vanessa runner: файл run_vanessa.bat.

При открытии основной формы `TestForFormModificator` автоматически запускается
весь зарегистрированный набор проверок. Вверху формы показаны итоговые количества
и протокол со статусом, названием проверки, проверяемым условием и фактическим
значением рядом с ожидаемым. Для упавшей проверки приводится причина. Кнопка
«Повторить автотесты» запускает набор заново. Дополнительные формы используются
как скрытые тестовые сценарии; открывать их вручную не требуется.

Проверка динамического списка сейчас подтверждает его создание и очистку свойств
контекста. Выполнение запроса и получение данных этот сценарий не проверяет.

Итог относится к зарегистрированным автоматическим проверкам, а не ко всем
возможным сценариям работы платформы. Счётчики вызовов на странице
«Итоговая таблица» относятся к демонстрации и не заменяют результаты автотестов.
Если общий модуль возвращён к исходной версии, проверки ещё не реализованных
исправлений #6, #7 и #9 показывают FAIL. Сообщение «Все проверки пройдены»
появляется только при отсутствии ошибок.

### Повторное использование контекста и обработчики

После успешного создания элемента из `Контекст.Свойства` удаляются
`ПутьКДанным` и `Заголовок`. Остальные свойства сохраняются. Это относится
также к командам и динамическим спискам. При повторном использовании контекста
задавайте путь и заголовок для каждого следующего элемента заново.

Обработчики задаются отдельно от свойств и применяются через
`УстановитьДействие`. После назначения структура обработчиков очищается,
чтобы они не переносились на следующий элемент:

```bsl
Контекст = РедакторФорм.НовыйКонтекстЭлемента(ЭтаФорма);
Контекст.Свойства.Вставить("Заголовок", "Комментарий");
Контекст.Обработчики.Вставить("ПриИзменении", "КомментарийПриИзменении");
РедакторФорм.НовоеПолеФормыРеквизитОбъекта(Контекст, "Комментарий");
```

Процедура `КомментарийПриИзменении(Элемент)` должна существовать в модуле
формы с директивой `&НаКлиенте`. Допустимые события и сигнатуры определяются
типом элемента. Для команд по-прежнему используется параметр `ИмяДействия`
функции `НоваяКомандаФормы`.

Функции добавления полей объекта автоматически находят единственный
объектный реквизит формы, включая реквизит с именем, отличным от `Объект`.
Если таких реквизитов несколько, укажите нужное имя явно:

```bsl
Контекст.ИмяРеквизитаОбъекта = "ДанныеДокумента";
```

Явно заданный `Контекст.Свойства.ПутьКДанным` имеет приоритет. Автоопределение
использует типы реквизитов, поскольку доступное описание `РеквизитФормы`
не содержит признака основного реквизита; неоднозначность вызывает исключение.

### Сборка расширения

Экспортируйте актуальный проект `FormEditor` из EDT в XML формата
Конфигуратора. Затем выполните (Python 3.9+):

```sh
python3 scripts/build-extension.py \
  --platform "/path/to/1cv8" \
  --source "/path/to/designer-xml-export" \
  --output "build/FormEditor.cfe"
```

Скрипт использует `ibcmd`, расположенный рядом с `1cv8` (либо переданный
непосредственно в `--platform`), создаёт временную файловую базу,
загружает XML в явно созданное расширение `FormEditor` и выгружает `.cfe`.
В расширение включается только общий модуль
`РедакторФорм`; тестовая обработка, язык и модуль приложения не включаются.
Код модуля копируется из экспорта без изменений. Для сборки требуется
консольная утилита `ibcmd` платформы 1С. Для проверки через графический
конфигуратор и запуска форм требуется доступная лицензия. Существующий выходной файл
не перезаписывается.

Для отдельной подготовки XML расширения:

```sh
python3 scripts/prepare-extension.py /path/to/designer-xml-export build/extension-xml
python3 -m unittest discover -s tests -v
```

Подключайте `.cfe` через управление расширениями в целевой базе, где ещё нет
общего модуля `РедакторФорм`. При переходе с поставки `.cf` сначала устраните
конфликт одноимённых модулей. Проверка сборки `.cfe` и работы в целевой
конфигурации необходима перед использованием расширения.

### Полная сборка и проверка в Docker

Правила release gate, статусы результатов, сравнение с известными runtime-сбоями
и условия публикации описаны в [docs/release-gate.md](docs/release-gate.md).

Для Linux ARM64 и x86_64 добавлены `docker/1c-release/` и
`scripts/run-container-release.sh`. Нужны Docker, Python 3.9+ на хосте,
установленный EDT и его каталог плагинов. Поместите пакеты платформы одной
версии и архитектуры (`common`, `server`, полный `client`) в отдельный каталог.
Пакеты и лицензии не входят в репозиторий или архив релиза.

```sh
ONEC_PACKAGE_DIR=/path/to/linux-platform-debs \
EDT_HOME=/path/to/edt/directory-with-configuration-and-1cedtcli \
EDT_PLUGIN_POOL=/path/to/edt/plugins \
ONEC_LICENSE_DIR=/path/to/valid-linux-licenses \
./scripts/run-container-release.sh
```

`ONEC_LICENSE_DIR` необязателен для сборки и проверки метаданных; для запуска
форм и проверки графическим конфигуратором процессу 1С нужна действующая
лицензия. Скрипт выводит путь к новому каталогу `build/release-run.*`.

В контейнере выполняются экспорт EDT, статическая проверка, Python-тесты,
сборка `.cf` и `.cfe`, применение конфигурации, установка расширения в базу
без общего модуля и обратная выгрузка для сравнения исходников. Затем
конфигуратор проверяет серверный, тонкий, веб-клиентский и внешнего соединения
контексты, а приложение запускает тот же набор проверок через основную форму в обоих
вариантах поставки. Проверяются очистка свойств, обработчики полей и таблиц, составные
вызовы, многострочные поля, переименованный и неоднозначный объектные реквизиты.

Результат содержит `.cf`, `.cfe`, исходный `.bsl`, `SHA256SUMS`, отчёты и
`manifest.json`. Полностью проверенный архив получает статус `verified`.
Если запуск заблокирован лицензией, сохраняется кандидат `-rc1`, в манифесте
явно отмечены заблокированные проверки, а скрипт возвращает код 2.
Ошибка сборки или установки расширения не создаёт архив релиза.
